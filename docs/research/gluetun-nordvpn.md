# Gluetun with NordVPN: credentials and server discovery

Research performed 2026-08-13 against current first-party NordVPN documentation and the official Gluetun documentation/source repository.

## Answer

The deployment utility does **not** need to generate a NordVPN access token or call NordVPN's API to discover a server for Gluetun.

Gluetun already ships a NordVPN server catalogue, selects a matching server from semantic filters, and can refresh its catalogue itself. Its documented NordVPN inputs are either:

- OpenVPN service username and password; or
- a WireGuard private key.

A Nord Account access token is a separate credential intended to log the official NordVPN Linux application into a headless device (and, in some supported router firmware, a token field). It is not one of Gluetun's documented NordVPN environment variables. Nord's token documentation offers a 30-day token or a non-expiring token, shows the token only once, recommends MFA for a non-expiring token, and permits revocation. It documents no selectable scopes. Logging out of the official Linux client revokes the token unless `--persist-token` is used. [NordVPN: token login on Linux](https://support.nordvpn.com/hc/en-us/articles/20286980309265-How-to-use-a-token-with-NordVPN-on-Linux)

Therefore the proposed stack should not own a Nord API client, request an access token, or store a token merely to configure Gluetun. Doing so would add a broad, long-lived account credential and an undocumented dependency without being required by Gluetun.

## Credential paths

### OpenVPN: supported, documented, and lowest onboarding risk

NordVPN requires the distinct **service credentials** shown under Nord Account's manual-setup area for manual OpenVPN connections; the user's normal account email/password is not valid for this purpose. [NordVPN server picker and manual credentials](https://support.nordvpn.com/hc/en-us/articles/19383127694225-Where-can-I-find-the-NordVPN-server-list) Gluetun agrees and requires:

```text
VPN_SERVICE_PROVIDER=nordvpn
VPN_TYPE=openvpn
OPENVPN_USER=<Nord service username>
OPENVPN_PASSWORD=<Nord service password>
```

`VPN_TYPE` may be omitted because Gluetun defaults it to OpenVPN, but declaring it is preferable for a generated deployment. `OPENVPN_PROTOCOL` is optional and defaults to UDP; TCP is the fallback for networks that block UDP. [Gluetun NordVPN provider setup](https://github.com/qdm12/gluetun-wiki/blob/main/setup/providers/nordvpn.md) [Gluetun OpenVPN options](https://github.com/qdm12/gluetun-wiki/blob/main/setup/options/openvpn.md)

The service credentials are displayed by Nord Account rather than generated by the stack CLI. Nord's official documentation does not state scopes or an expiry policy for them. Treat both values as durable secrets and support replacement, but do not invent an expiry guarantee.

### WireGuard/NordLynx: supported by Gluetun, but first-party guidance conflicts

Gluetun documents native NordVPN WireGuard support and requires:

```text
VPN_SERVICE_PROVIDER=nordvpn
VPN_TYPE=wireguard
WIREGUARD_PRIVATE_KEY=<base64 private key>
```

For NordVPN, Gluetun does not document `WIREGUARD_ADDRESSES` as required. [Gluetun NordVPN provider setup](https://github.com/qdm12/gluetun-wiki/blob/main/setup/providers/nordvpn.md) [Gluetun WireGuard setup](https://github.com/qdm12/gluetun-wiki/blob/main/setup/wireguard.md)

However, NordVPN's current public documentation says NordLynx is proprietary to its apps and that Nord does not provide exportable WireGuard configuration files for third-party clients. [NordVPN configuration files](https://nordvpn.com/blog/nordvpn-config-files/) This conflicts with Gluetun's statement that the WireGuard private key can be retrieved from Nord Account's manual-setup web interface. The Gluetun page's linked acquisition discussion is old, and neither current official source documents a stable API contract for converting an access token into a private key.

Nord recommends NordLynx generally and uses it by default because it is faster; it recommends OpenVPN when stability/compatibility is the priority. [NordVPN protocol guidance](https://support.nordvpn.com/hc/en-us/articles/19482810153745-Which-NordVPN-protocol-should-I-choose) For this third-party Gluetun deployment, operational supportability outweighs protocol benchmarks: **use OpenVPN UDP for the first milestone**, with OpenVPN TCP as an explicit troubleshooting fallback. Make WireGuard an optional later mode only after a human can obtain a private key through a currently supported Nord Account UI and an end-to-end test proves it. Do not automate an undocumented token-to-key API flow.

## Server discovery and selection

The stack CLI should express intent and leave endpoint discovery to Gluetun:

- use `SERVER_COUNTRIES`, optionally narrowed by `SERVER_REGIONS`, `SERVER_CITIES`, or `SERVER_CATEGORIES`;
- avoid a single `SERVER_HOSTNAMES` value in normal configuration, because Gluetun warns that a hostname can disappear from refreshed data and prevent startup;
- do not scrape Nord's account server picker or query an undocumented Nord API during `plan` or `apply`.

Gluetun merges server data built into the image with the persisted `/gluetun/servers/` catalogue. `format-servers -nordvpn` reports the filters supported by the pinned image. Its updater is disabled by default; the official guidance recommends a period no shorter than 360 hours and gives 480 hours as an example. Periodic refresh occurs only after the tunnel is ready, through the VPN and DNS over HTTPS. A CLI update is available for recovery when all embedded data is stale, although it exposes the host's public IP to the configured DNS-over-HTTPS resolvers while resolving endpoints. [Gluetun server list and updater](https://github.com/qdm12/gluetun-wiki/blob/main/setup/servers.md)

Recommended generated settings:

```text
SERVER_COUNTRIES=Canada
SERVER_CATEGORIES=P2P
UPDATER_PERIOD=480h
```

`SERVER_CATEGORIES=P2P` must first be validated against `format-servers -nordvpn` for the pinned Gluetun image; filter vocabulary is image/catalogue data, not a stable assumption. Country should be a user-configurable semantic value, with Canada merely a local default candidate. Persist `/gluetun` so refreshed server data survives container replacement.

## Firewall, network sharing, and health

Gluetun's firewall is enabled by default, starts before its proxy services, never turns off during normal operation, and allows outbound traffic only to the selected VPN endpoint through the permitted tunnel path. It therefore acts as the kill switch when the tunnel goes down. `FIREWALL=off` is a debugging option, not an accepted deployed state. [Gluetun firewall behavior](https://github.com/qdm12/gluetun-wiki/blob/main/faq/firewall.md)

qBittorrent should use `network_mode: "service:gluetun"`, and all qBittorrent port publication must be declared on Gluetun because both containers share one network namespace. [Gluetun container networking](https://github.com/qdm12/gluetun-wiki/blob/main/setup/connect-a-container-to-gluetun.md)

The generated Gluetun service needs `NET_ADMIN` and `/dev/net/tun:/dev/net/tun`. Its image has a built-in healthcheck and auto-heals the VPN after failed connectivity checks; the stack must additionally gate qBittorrent startup/readiness on Gluetun becoming healthy. The stack must not enable NordVPN port forwarding: NordVPN is absent from Gluetun's list of providers with native port-forwarding support. [Gluetun README](https://github.com/qdm12/gluetun) [Gluetun port forwarding](https://github.com/qdm12/gluetun-wiki/blob/main/setup/advanced/vpn-port-forwarding.md)

LAN access is not automatically a reason to set `FIREWALL_OUTBOUND_SUBNETS`. Published Web UI ports arrive through Gluetun's Docker interface. Add outbound LAN CIDRs only for a concrete dependency that qBittorrent must initiate toward the LAN; broad private-address ranges weaken the fail-closed boundary.

## Secret injection

Prefer Compose secrets rather than rendered environment values. Gluetun has native secret-file names:

```yaml
services:
  gluetun:
    secrets:
      - openvpn_user
      - openvpn_password

secrets:
  openvpn_user:
    file: <runtime plaintext file>
  openvpn_password:
    file: <runtime plaintext file>
```

They appear inside the container at `/run/secrets/openvpn_user` and `/run/secrets/openvpn_password`; Gluetun also supports `OPENVPN_USER_SECRETFILE` and `OPENVPN_PASSWORD_SECRETFILE` to override those paths. WireGuard similarly supports `wireguard_private_key` / `WIREGUARD_PRIVATE_KEY_SECRETFILE`. [Gluetun Docker secrets](https://github.com/qdm12/gluetun-wiki/blob/main/setup/advanced/docker-secrets.md)

Compose secrets are file mounts, not a general mechanism that decrypts SOPS. The CLI still must decrypt to a tightly permissioned runtime file (or equivalent file descriptor/materialization), grant the secret only to Gluetun, and remove ephemeral plaintext after Compose has consumed it without breaking the active mount. Docker warns that environment variables can leak through process inspection or logs and notes that `_FILE` support is image-specific. [Docker Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/)

Gluetun says it unsets sensitive environment variables after reading them, but this does not prevent exposure in generated Compose configuration, shell history, Docker inspection before startup, or CLI logs. The existing semantic SOPS shape should consequently remain protocol-specific:

```yaml
nordvpn:
  openvpn:
    serviceUsername: <secret>
    servicePassword: <secret>
```

If WireGuard is later enabled, add a mutually exclusive `nordvpn.wireguard.privateKey`; do not add an access token unless a separate, documented feature actually consumes it.

## Testable acceptance requirements

The same black-box suite should run on native Ubuntu and Docker Desktop's WSL2 backend. A platform preflight may differ; the security outcomes may not.

1. **Prerequisites:** Docker Engine/Compose can start a pinned Gluetun image with `NET_ADMIN` and `/dev/net/tun`; failure produces an actionable prerequisite error without printing secrets.
2. **Credential contract:** configuration accepts exactly one supported protocol credential set. The first milestone accepts Nord service username/password, rejects account email/password guidance, and never asks for an access token/API key.
3. **No CLI Nord API dependency:** `plan` is offline with respect to NordVPN and renders semantic filters, not an endpoint. `apply` delegates catalogue use/update to Gluetun and does not send account credentials or tokens to a stack-owned Nord API client.
4. **Secret handling:** `docker compose config`, CLI output, logs, and persisted generated configuration contain no credential values. Only Gluetun receives the two Compose secret mounts. Runtime plaintext has owner-only permissions and follows the declared cleanup lifecycle.
5. **Tunnel readiness:** Gluetun becomes healthy within a bounded timeout; logs identify OpenVPN UDP, the selected country/category, and a successful tunnel without leaking credentials.
6. **Egress proof:** an external IP check from qBittorrent's shared namespace returns a public IP different from a host-side check. DNS resolution from that namespace succeeds after tunnel readiness.
7. **Fail closed:** after deliberately stopping the VPN through Gluetun or making the endpoint unreachable, a new egress attempt from qBittorrent's namespace fails. It must not return the host public IP. Recovery restores health and tunneled egress.
8. **Namespace isolation:** qBittorrent has `network_mode: service:gluetun`, no independently attached network, and no published ports of its own; its Web UI is reachable only through the port published by Gluetun.
9. **Server resilience:** configuration uses country/category filters. The pinned image can run `format-servers -nordvpn`, finds at least one matching OpenVPN UDP server, and a persisted catalogue refresh succeeds with `UPDATER_PERIOD` at least 360h.
10. **Negative tests:** invalid service credentials, an empty filter result, missing TUN support, and loss of VPN connectivity each fail with distinguishable diagnostics and never permit direct qBittorrent egress.
11. **Platform matrix:** all preceding assertions pass on native Ubuntu and WSL2. WSL2-specific host/TUN setup, if any is discovered in CI, remains a preflight adapter rather than a weakened networking mode; `privileged: true`, host networking, and `FIREWALL=off` are prohibited workarounds.

## Consequences for existing stories and configuration design

- Replace the generic `nordvpn.username/password` wording with **NordVPN OpenVPN service username/password**.
- Add a decision that OpenVPN UDP is the first-milestone protocol, with TCP as a fallback and WireGuard deferred behind a supported-key-acquisition proof.
- Remove any story requiring the stack CLI to generate/store a Nord access token or query Nord's API for server choice.
- Add server-filter fields (country required by product policy; region/city/category optional) and a catalogue update interval constrained to `>=360h` when enabled.
- Add explicit stories for secret-file rendering, pinned-image `format-servers` validation, tunnel health, egress identity, forced-tunnel fail-closed behavior, and the Ubuntu/WSL2 platform matrix.
- Preserve NordVPN as a replaceable provider boundary and keep port forwarding disabled.

## Uncertainty requiring a product decision

The only material documentation conflict is WireGuard key acquisition. Gluetun claims a key is obtainable from Nord Account; Nord says it does not export WireGuard configurations and NordLynx is app-only. Neither current public source provides a supported, scoped token-to-key API contract. This is sufficient reason not to make token/API automation part of the design. A future WireGuard story should begin with a human verification task against the live Nord Account UI, followed by a disposable end-to-end prototype; it should not assume an unofficial API remains available.

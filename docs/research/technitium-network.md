# Technitium DNS and DHCP for the home network

Research performed 2026-10-14. Primary sources are Technitium's documentation, tagged v15.6.1 source/API documentation, project-owned tool repositories, and DNS RFCs. This is design research; no live network behavior has been tested.

## Version and installation

Technitium v15.6.1 was released on 11 October 2026. Version 15 moved the native Linux service to .NET 10 and changed the installer to run as a non-root systemd service. Pin and test one version on both hosts; the v14.1 and v14.2 changelog records cluster API and compatibility breaks, so avoid staggered upgrades without an explicit compatibility check. [Technitium changelog](https://github.com/TechnitiumSoftware/DnsServer/blob/v15.6.1/CHANGELOG.md)

The project explicitly supports Linux/Raspberry Pi installation and supplies an official Docker image. This confirms an installation path, **not** acceptable Pi 3 Model B performance under recursion, filtering, and clustering; measure memory, latency, and recovery on that exact Pi before treating it as a dependable secondary. [Technitium README](https://github.com/TechnitiumSoftware/DnsServer/tree/v15.6.1#installation) [Official download page](https://technitium.com/dns/)

For DHCP in Docker, Technitium's example directs `network_mode: host` and removal of published `ports`. The Ubuntu deployment therefore needs a port inventory and a host-networked container with persistent `/etc/dns`; check conflicts with host DNS and other Docker services before rollout. The Pi can use the native systemd installer. [Official Compose example](https://github.com/TechnitiumSoftware/DnsServer/blob/v15.6.1/docker-compose.yml)

## Cluster and DNS failure behavior

**Confirmed:** Cluster nodes still run independent DNS services. The primary owns cluster configuration changes; secondary nodes sync by notification and periodic refresh and may be manually promoted after primary failure. Cluster-wide Allowed, Blocked, Apps, users, groups, permissions, and API tokens sync. Cache, logs, sessions, node-specific settings, and DHCP scopes do not. Ordinary zones remain independent unless added to the special cluster catalog; member zones are provisioned on secondaries, with cluster-managed NS/SOA records. [Technitium clustering guide](https://blog.technitium.com/2025/11/understanding-clustering-and-how-to.html)

**Confirmed:** The cluster uses node-to-node TLS with DANE-EE, and its guide warns against terminating that connection at an HTTPS reverse proxy. The pilot must establish the concrete listening ports, firewall policy, certificate/bootstrap process, and join behavior on the pinned release. [Technitium clustering guide](https://blog.technitium.com/2025/11/understanding-clustering-and-how-to.html)

**Inference:** A 72-hour primary outage target requires the Pi's `home` secondary zone to remain authoritative for longer than 72 hours without a refresh. The SOA EXPIRE field is the upper bound before a secondary ceases to be authoritative. Configure a margin beyond 72 hours, then actually stop the primary and test the secondary zone through the target interval; promotion is a separate manual recovery path. External recursion and caching should be tested independently on each node. [RFC 1035, SOA EXPIRE](https://www.rfc-editor.org/rfc/rfc1035.html#section-3.3.13) [Technitium clustering guide](https://blog.technitium.com/2025/11/understanding-clustering-and-how-to.html)

## DHCP scope, reservations, and DNS updates

**Confirmed:** Technitium's scope API has start/end, subnet mask, gateway, DNS server list, domain name, exclusions, reservations, DNS updates, and DNS TTL fields. The domain name option enables automatic forward and reverse entries for allocated addresses when DNS updates are enabled. `useThisDnsServer=true` overrides the explicit DNS list; use `false` when advertising both servers. [v15.6.1 DHCP scope API](https://github.com/TechnitiumSoftware/DnsServer/blob/v15.6.1/APIDOCS.md#dhcp-api-calls)

**Design inference to test:** Technitium has historically required a reservation address to be inside the scope range; a project issue documents that limitation, and the API describes exclusions as preventing **dynamic** allocation. Set the scope start to the first reserved address and its end to the last dynamic address, then exclude the reserved-address band from dynamic allocation. Keep statically configured Hosts outside the scope. Test a reserved client inside the exclusion and an unreserved client in the dynamic band before cutover: if v15.6.1 rejects reserved addresses in an exclusion, change the design before enabling DHCP. Actual Site addresses and ranges belong only in the SOPS-encrypted inventory. [Technitium DHCP scope API](https://github.com/TechnitiumSoftware/DnsServer/blob/v15.6.1/APIDOCS.md#dhcp-api-calls) [Project issue on out-of-range reservations](https://github.com/TechnitiumSoftware/DnsServer/issues/831)

**Confirmed:** The scope API includes `dnsUpdates`, `dnsTtl`, reservation hostname overrides, and an option introduced in v14.3 to allow a dynamic lease to overwrite an existing A record. Default to refusing overwrites of declared service names. **Pilot questions:** verify A/PTR creation, renewal and expiry cleanup, reservation hostname precedence, and whether DHCP-generated records from the primary appear in the Pi's cluster-catalog secondary promptly and survive primary loss. Do not promise these lifetime details from the API description alone. [v15.6.1 DHCP API](https://github.com/TechnitiumSoftware/DnsServer/blob/v15.6.1/APIDOCS.md#dhcp-api-calls) [Technitium changelog](https://github.com/TechnitiumSoftware/DnsServer/blob/v15.6.1/CHANGELOG.md)

The server running DHCP needs a static OS-level address. The project maintainer states that its DHCP service will not start when that host address was obtained by DHCP. [Maintainer answer](https://github.com/TechnitiumSoftware/DnsServer/discussions/817)

## Backup, restore, and permissions

**Confirmed:** The backup API can include DHCP scope files (`scopes=true`), zone files, DNS settings, authentication configuration, apps, and other selected data in a ZIP. Restore accepts selected components and an optional `deleteExistingFiles`; both backup and restore require `Settings: Delete`, a broad permission that should belong to a separately protected backup identity rather than the routine reconciler. Lease listing needs `DhcpServer: View`; modifying scopes/reservations needs `DhcpServer: Modify`; lease deletion needs `DhcpServer: Delete`. [v15.6.1 backup/restore and DHCP API](https://github.com/TechnitiumSoftware/DnsServer/blob/v15.6.1/APIDOCS.md)

**Inference requiring a restore test:** DHCP scope serialization appears to include active leases as well as reserved leases, but the API says only “scope files,” not an explicit lease-preservation guarantee. Prove that a backup restored on a disposable server preserves scope configuration, reservations, and active lease state before relying on it for DHCP rollback. Test restore without accidentally enabling a second DHCP responder. [v15.6.1 `Scope.cs`](https://github.com/TechnitiumSoftware/DnsServer/blob/v15.6.1/DnsServerCore/Dhcp/Scope.cs) [v15.6.1 backup API](https://github.com/TechnitiumSoftware/DnsServer/blob/v15.6.1/APIDOCS.md)

Version 15 requires bearer session tokens in the `Authorization` header for authenticated API calls. Automation and candidate libraries must be tested against that contract; avoid embedding a token in a query string or deployment logs. [v15.6.1 API documentation](https://github.com/TechnitiumSoftware/DnsServer/blob/v15.6.1/APIDOCS.md)

## Infrastructure-as-code candidates

- **Ansible:** `effectivelywild.technitium_dns` documents DNS, DHCP-scope, and cluster modules, and has a `set_dhcp_scope` module. It is a plausible first pilot for idempotence and dry run. Its published module documentation identifies collection 1.1.2; verify v15 bearer authentication, check mode, diffs, reservation updates/deletes, and cluster-zone handling against pinned v15.6.1 before adoption. [Collection repository](https://github.com/effectivelywild/ansible-collection-technitium-dns) [Scope module documentation](https://effectivelywild.github.io/ansible-collection-technitium-dns/collections/effectivelywild/technitium_dns/technitium_dns_set_dhcp_scope_module.html)
- **Terraform/OpenTofu:** Community Technitium providers exist, but capabilities vary. The `yordis` provider describes individual DNS-record management; `bartei` documents DHCP-scope resources and warns that nested and standalone reservation resources can fight over the same list. Terraform state would also contain managed IPs/MACs unless encrypted and access-controlled. Evaluate only after inventory encryption and state handling are designed. [yordis provider](https://github.com/yordis/terraform-provider-technitium) [bartei DHCP scope resource](https://registry.terraform.io/providers/bartei/technitium/latest/docs/resources/dhcp_scope)
- **Python:** `Atlas-Commons/technitiumdns-api` advertises synchronous/asynchronous clients and bearer-token support. It is a client, not a complete desired-state reconciler; test coverage of cluster, scopes, reservations, and v15.6.1 before adding custom planning or reconciliation code. [Client repository](https://github.com/Atlas-Commons/technitiumdns-api)

The Technitium API documentation says `set` calls overwrite their managed value and `add` calls append. No transaction or atomic multi-resource apply guarantee was found. A safe reconciler should read and diff live state, snapshot before applying, use narrowly scoped operations, verify afterward, and keep deletion behind the agreed manual gate. This is a proposed operating method, not a documented Technitium transaction feature. [v15.6.1 API documentation](https://github.com/TechnitiumSoftware/DnsServer/blob/v15.6.1/APIDOCS.md)

## Minimum disposable pilot

1. Confirm host-networked Docker DHCP packets reach a test LAN and there is exactly one responding DHCP server; test a reservation inside the excluded band and unreserved allocation only inside the declared dynamic band.
2. Join native Pi and Docker homelab nodes on v15.6.1; verify cluster authentication and required ports, catalog-zone replication, DNS filtering sync, independent recursion, and Pi 3 memory/latency.
3. Verify dynamic A/PTR creation, lease changes, expiry cleanup, reservation hostname behavior, overwrite protection, and replication to the Pi.
4. Stop homelab for more than 72 hours in a disposable setup or use a controlled clock/shortened SOA interval to validate expiry mechanics; then test documented promotion and rejoin.
5. Backup and restore to an isolated server; inspect scope, reservations, leases, zone data, authentication, and whether a service restart was required.
6. Pin candidate IaC versions and prove dry run, unchanged second apply, updates, deliberate deletion, drift detection, v15 bearer auth, and rollback before choosing a tool.

# `automation-avenue/arr-new` Compose evaluation

Research performed 2026-08-14 against Automation Avenue's 52-minute [New ARR Stack setup video](https://www.youtube.com/watch?v=-PQtE6Nb0Cw) and repository revision [`6d07177a07858e6ca59474168229b3242e3ac4f2`](https://github.com/automation-avenue/arr-new/commit/6d07177a07858e6ca59474168229b3242e3ac4f2), committed 2026-02-01. The repository's Compose file is the primary source for topology; its README and video are the primary sources for the intended operator workflow.

## Answer

Use `arr-new` as a teaching reference, not as a Compose base to copy or fork.

Its strongest contribution is a coherent storage and application-path convention: one `/data` mount contains both downloads and libraries, qBittorrent categories select subdirectories below `/data/torrents`, and Radarr/Sonarr import into sibling paths below `/data/media`. That is the right shape for hardlinks and atomic renames and should be made exact in this plan. Its use of service names for internal application URLs, a read-only Jellyfin media mount, an explicit restart policy, and an end-to-end legal acquisition followed by inode verification are also useful patterns.

The topology itself is not suitable for this Home Media Stack. It has no VPN service, gives qBittorrent an ordinary bridge-network route, publishes qBittorrent's Web UI and torrent ports directly, hard-codes global container/network names, uses mutable `latest` images, has no healthchecks or dependency gating, and relies on manual UI configuration. Most importantly, the video describes selecting Cloudflare resolvers as “Secure DNS over a traditional VPN”; the Compose file only sets `dns: 1.1.1.1` and `1.0.0.1`. Docker documents `dns` as selecting custom resolvers, while actual encrypted DNS requires a DoH or DoT client/protocol. This setting neither encrypts DNS by itself nor tunnels or fail-closes qBittorrent traffic. [Upstream common settings](https://github.com/automation-avenue/arr-new/blob/6d07177a07858e6ca59474168229b3242e3ac4f2/docker-compose.yml#L4-L15) [Docker Compose `dns`](https://docs.docker.com/reference/compose-file/services/#dns) [Cloudflare DoH](https://developers.cloudflare.com/1.1.1.1/encryption/dns-over-https/) [Cloudflare DoT](https://developers.cloudflare.com/1.1.1.1/encryption/dns-over-tls/) [Video DNS check, 50:35](https://www.youtube.com/watch?v=-PQtE6Nb0Cw&t=3035s)

The existing decisions remain stronger and should not be weakened: cross-platform rendered Compose plus CLI reconciliation, isolated Production and Staging Environments, pinned versions, SOPS-backed secret handling, and qBittorrent sharing Gluetun's fail-closed network namespace. [Cross-platform Compose ADR](../adr/0001-cross-platform-compose-media-stack.md) [environment-isolation ADR](../adr/0003-isolate-production-and-staging.md) [Gluetun/NordVPN research](gluetun-nordvpn.md)

## What the upstream stack actually does

### Service composition and topology

The Compose project contains Radarr, Sonarr, Lidarr, Bazarr, Prowlarr, qBittorrent, and Jellyfin. Every service joins one default bridge network explicitly named `arr_network`; each also has a fixed `container_name`. All seven images use the mutable `latest` tag. [Radarr and Sonarr](https://github.com/automation-avenue/arr-new/blob/6d07177a07858e6ca59474168229b3242e3ac4f2/docker-compose.yml#L19-L42) [Lidarr through Prowlarr](https://github.com/automation-avenue/arr-new/blob/6d07177a07858e6ca59474168229b3242e3ac4f2/docker-compose.yml#L47-L84) [qBittorrent and Jellyfin](https://github.com/automation-avenue/arr-new/blob/6d07177a07858e6ca59474168229b3242e3ac4f2/docker-compose.yml#L88-L116) [network](https://github.com/automation-avenue/arr-new/blob/6d07177a07858e6ca59474168229b3242e3ac4f2/docker-compose.yml#L121-L123)

The README then configures application-to-application connections by Docker service name: Prowlarr and the Arr applications reach `qbittorrent:8080`, and Prowlarr reaches `radarr:7878`, `sonarr:8989`, and `lidarr:8686`. This is the useful part of the dedicated network; the fixed `container_name` values are unnecessary for service discovery. [Prowlarr/qBittorrent connection](https://github.com/automation-avenue/arr-new/blob/6d07177a07858e6ca59474168229b3242e3ac4f2/README.md#L57-L65) [Prowlarr/Arr connections](https://github.com/automation-avenue/arr-new/blob/6d07177a07858e6ca59474168229b3242e3ac4f2/README.md#L66-L102)

There is no Gluetun or other VPN container. qBittorrent has independent default-network egress and directly publishes `8080`, TCP `6881`, and UDP `6881`. A dedicated bridge network provides service discovery and some project-level grouping; it is not an egress-security boundary. [qBittorrent service](https://github.com/automation-avenue/arr-new/blob/6d07177a07858e6ca59474168229b3242e3ac4f2/docker-compose.yml#L88-L102)

### Storage and path conventions

The host layout is `/data/torrents/{tv,movies,music}` beside `/data/media/{tv,movies,music}`. Radarr, Sonarr, Lidarr, and qBittorrent each receive the entire host `/data` tree at container path `/data`; their configuration uses `/data/torrents` for downloads and `/data/media/<library>` for library roots. Keeping source and destination inside the same mounted filesystem permits hardlinks and atomic moves. [Host layout and rationale](https://github.com/automation-avenue/arr-new/blob/6d07177a07858e6ca59474168229b3242e3ac4f2/README.md#L13-L27) [service mounts](https://github.com/automation-avenue/arr-new/blob/6d07177a07858e6ca59474168229b3242e3ac4f2/docker-compose.yml#L19-L56)

qBittorrent uses Automatic Torrent Management with category save paths `movies`, `tv`, and `music`, relative to `/data/torrents`. Radarr and Sonarr use corresponding categories and `/data/media/movies` or `/data/media/tv` roots. [qBittorrent categories and save path](https://github.com/automation-avenue/arr-new/blob/6d07177a07858e6ca59474168229b3242e3ac4f2/README.md#L40-L55) [Radarr and Sonarr settings](https://github.com/automation-avenue/arr-new/blob/6d07177a07858e6ca59474168229b3242e3ac4f2/README.md#L66-L93)

Jellyfin receives only `/data/media`, mounted read-only. Bazarr receives `/data/media` read-write because its job includes writing subtitle files. [Jellyfin mount](https://github.com/automation-avenue/arr-new/blob/6d07177a07858e6ca59474168229b3242e3ac4f2/docker-compose.yml#L107-L116) [Bazarr mount](https://github.com/automation-avenue/arr-new/blob/6d07177a07858e6ca59474168229b3242e3ac4f2/docker-compose.yml#L61-L70)

### Health, dependencies, and operations

The only lifecycle policy is `restart: unless-stopped`. There are no Compose healthchecks or `depends_on` relationships, so `docker compose up -d` means containers were started, not that their APIs or acquisition path are ready. The documented recovery action is a whole-project `down` followed by `up -d`. [common lifecycle settings](https://github.com/automation-avenue/arr-new/blob/6d07177a07858e6ca59474168229b3242e3ac4f2/docker-compose.yml#L4-L15) [start/restart workflow](https://github.com/automation-avenue/arr-new/blob/6d07177a07858e6ca59474168229b3242e3ac4f2/README.md#L21-L23) [restart workflow](https://github.com/automation-avenue/arr-new/blob/6d07177a07858e6ca59474168229b3242e3ac4f2/README.md#L108-L112)

The tutorial's best operational check is behavioral: download a public-domain item, verify the import, then compare source and destination inode numbers to prove a hardlink. That aligns well with this repository's existing legal test-item and hardlink acceptance stories. [Video public-domain acquisition, 44:25](https://www.youtube.com/watch?v=-PQtE6Nb0Cw&t=2665s) [Video inode check, 47:15](https://www.youtube.com/watch?v=-PQtE6Nb0Cw&t=2835s) [README inode check](https://github.com/automation-avenue/arr-new/blob/6d07177a07858e6ca59474168229b3242e3ac4f2/README.md#L128-L141)

### Configuration, identities, and secrets

The common anchor hard-codes UID `1000`, GID `1000`, `Europe/London`, Cloudflare resolver IPs, and `/etc/localtime`; app configs are fixed host bind mounts below `/docker/appdata`. The README recommends recursively changing `/data` ownership and permissions to match `1000:1000`. Those choices are convenient for a fresh single-host tutorial but are not safe assumptions for existing household data or portable Ubuntu/WSL hosts. [common settings](https://github.com/automation-avenue/arr-new/blob/6d07177a07858e6ca59474168229b3242e3ac4f2/docker-compose.yml#L4-L15) [host preparation](https://github.com/automation-avenue/arr-new/blob/6d07177a07858e6ca59474168229b3242e3ac4f2/README.md#L13-L14)

There is also a subtle YAML-merge hazard: qBittorrent declares its own `environment` sequence, which replaces the anchor's entire `environment` mapping. Consequently qBittorrent does not inherit the common PUID, PGID, or timezone even though it inherits the other top-level common keys. This is a reason for generated structural tests rather than reliance on a broad service-level anchor. [common environment](https://github.com/automation-avenue/arr-new/blob/6d07177a07858e6ca59474168229b3242e3ac4f2/docker-compose.yml#L4-L14) [qBittorrent override](https://github.com/automation-avenue/arr-new/blob/6d07177a07858e6ca59474168229b3242e3ac4f2/docker-compose.yml#L88-L102)

Credentials, API keys, categories, library roots, and inter-application links are entered manually in web UIs. qBittorrent's temporary administrator password is read from container logs; application API keys are copied between UIs. The configuration does persist in per-service appdata, but there is no declared configuration, convergence check, redaction contract, or backup manifest. [qBittorrent bootstrap](https://github.com/automation-avenue/arr-new/blob/6d07177a07858e6ca59474168229b3242e3ac4f2/README.md#L29-L39) [manual API-key linking](https://github.com/automation-avenue/arr-new/blob/6d07177a07858e6ca59474168229b3242e3ac4f2/README.md#L66-L102)

## Adopt

1. **One in-container `/data` seam per environment.** Give qBittorrent, Radarr, and Sonarr the same `/data` mount root so download and library paths resolve to one filesystem. Preserve identical container paths in Production and Staging while binding distinct host subtrees.
2. **Exact first-milestone paths.** Use `/data/torrents/movies`, `/data/torrents/series`, `/data/media/movies`, and `/data/media/series`. Use qBittorrent category save paths `movies` and `series`; make Radarr and Sonarr consume exactly those declared categories. “Series” matches this repository's domain language better than the tutorial's `tv` label.
3. **Behavioral hardlink proof.** Retain the existing same-device, hardlink, atomic-rename, and inode-equality checks. The video's legal acquisition plus inode verification is a good black-box acceptance shape, though the exact Public Torrent Source and fixture still require their own approval.
4. **Read-only Jellyfin library access.** Mount the selected environment's `/data/media` into Jellyfin read-only, in addition to disabling destructive deletion in Jellyfin policy. Playback does not require Jellyfin to mutate the Movie or Series Library.
5. **Internal service endpoints.** Continue using stable Compose DNS names rather than host-published ports for Prowlarr, Radarr, Sonarr, and qBittorrent integrations.
6. **Restart policy.** `unless-stopped` is a reasonable default for long-running household services when paired with health and readiness checks.

## Adapt

1. **Make runtime identity declared and verified.** Replace hard-coded `1000:1000` with semantic `runtimeUID` and `runtimeGID` Declared Configuration, defaulted from the intended host operator only when discoverable and explicitly shown. `doctor` should verify ownership, read/write access, hardlink creation, and atomic rename. Never recursively `chown` an existing data root merely because a tutorial assumes UID 1000.
2. **Make host storage environment-specific.** A suitable host shape is `<dataRoot>/production/{torrents,media}/...` and `<dataRoot>/staging/{torrents,media}/...`, with only the selected environment root mounted as `/data`. Service config roots likewise need environment identity and complete backup coverage; do not use global `/docker/appdata/<service>` paths.
3. **Preserve a qBittorrent DNS name through Gluetun.** Once qBittorrent uses `network_mode: service:gluetun`, it no longer owns an attachment or alias on the application network. Attach Gluetun to that environment's application network and give that attachment a `qbittorrent` network alias (or reconcile one documented alternative endpoint such as `gluetun:8080`). This preserves the tutorial's useful `qbittorrent:8080` application contract without giving qBittorrent an independent route. The qBittorrent Web UI host port remains published only by Gluetun.
4. **Use environment-scoped Compose names.** Let Compose derive resource names from the distinct Production/Staging project names. If a network needs an explicit name, render an environment-qualified one. Do not carry over `container_name: radarr` or the global `arr_network`, which collide when both environments run on one host.
5. **Gate readiness, not merely start order.** Add healthchecks appropriate to each pinned image. qBittorrent should depend on healthy Gluetun using `condition: service_healthy`; the CLI should poll supported service APIs with bounded, diagnosable waits before reconciliation. Docker explicitly distinguishes service start from `service_healthy`. [Docker Compose dependency conditions](https://docs.docker.com/reference/compose-file/services/#depends_on)
6. **Keep common settings typed and test rendered output.** Reuse renderer-level defaults for restart policy, timezone, logging, and runtime identity, but structurally assert each service's final values. Avoid a single YAML anchor whose nested mappings can be silently replaced. Prefer a timezone value over binding host `/etc/localtime`, which is unnecessary and less portable on Docker Desktop/WSL.
7. **Bound logs.** The tutorial explicitly selects `json-file` but supplies no rotation options. Render a bounded logging policy or document a required daemon-level policy so service logs cannot grow without limit.
8. **Keep only declared service scope.** Radarr, Sonarr, Prowlarr, qBittorrent, and Jellyfin map to the current milestone. Do not add Lidarr, Bazarr, SABnzbd, or FlareSolverr because they appear in the tutorial. They require separate product decisions, policy, credentials, writable paths, health checks, backup coverage, and acceptance tests.
9. **Turn manual configuration into reconciliation.** The walkthrough is useful for identifying supported UI concepts—root folders, categories, application links, authentication—but this stack should reconcile them through supported APIs and prove repeated `apply` is empty. Retain a guided UI step only where an API genuinely cannot perform it, as already decided for Profilarr.
10. **Treat persistent config as secret-bearing state.** Environment-specific config volumes contain passwords, API keys, and tokens even when Compose does not. Include every mutable service volume in encrypted/access-controlled backups and redact CLI output, logs, fixtures, manifests, and verification artifacts.

## Reject

1. **Reject “Secure DNS instead of VPN.”** The video's own description says it uses Secure DNS over a traditional VPN, and its final check only inspects resolver behavior. The Compose file merely selects Cloudflare DNS servers; it does not configure DoH/DoT, change qBittorrent's public egress IP, or provide a kill switch. Keep Gluetun, its firewall, shared namespace, egress-identity comparison, forced-tunnel interruption, and recovery proof exactly as planned.
2. **Reject independent qBittorrent networking and ports.** Do not attach qBittorrent to the default bridge, publish ports on qBittorrent, or expose `6881` merely because the example does. NordVPN does not provide the planned Gluetun port-forwarding path, and direct qBittorrent egress violates the stack's primary security invariant.
3. **Reject mutable images.** Every upstream service uses `latest`. This defeats reproducible plan/apply, fixture compatibility, exact Staging verification, and Promotion. Keep checked-in versions and immutable digests where supported.
4. **Reject fixed global resource names.** Fixed `container_name` values and `arr_network` prevent safe simultaneous Production and Staging projects and bypass normal Compose project scoping.
5. **Reject hard-coded UID/GID, timezone, DNS, and absolute appdata paths.** They encode one author's machine, not portable host intent.
6. **Reject `up -d` as readiness or verification.** A successful container start is not a healthy VPN, reachable API, reconciled policy, legal acquisition, hardlink import, playback path, or fail-closed result.
7. **Reject manual UI state as the normal operating model.** Copying passwords and API keys from logs/UI and relying on screenshots or memory cannot support Declared Configuration, drift repair, safe backup/restore, or exact Promotion.
8. **Reject copying unlicensed source.** The upstream tree has no license file at the reviewed revision, and the repository publishes no tagged releases. Reimplement the small conceptual patterns in this repository's own renderer and tests; do not vendor or derive the Compose file text. ## Exact implications for the current plan

No new implementation ticket is necessary. Incorporate the useful details by strengthening the existing tickets under [Build the Home Media Stack](https://github.com/adkulas/homelab/issues/36):

- **#1 Render a pinned Compose project:** assert every rendered image is version/digest pinned; render and structurally test restart, bounded logging, timezone, and semantic runtime UID/GID; prohibit fixed `container_name` values and unqualified global resource names.
- **#2 Give each environment a distinct identity:** assert Production and Staging derive distinct project/network/config-volume/port names and can render concurrently without `arr_network` or container-name collisions.
- **#3 Initialize Declared Configuration:** collect or derive-with-confirmation `runtimeUID`, `runtimeGID`, timezone, and environment data/config roots without rewriting existing filesystem ownership.
- **#6 Provision an isolated data layout:** make the host and container contracts exact: environment-qualified host roots map to `/data`, with `torrents/{movies,series}` and `media/{movies,series}` beneath them.
- **#7 Verify storage capabilities:** perform the tutorial-inspired black-box checks with the declared runtime identity: writable directories, same device, hardlink creation with inode equality, atomic rename, and filesystem events.
- **#8/#9 Start Gluetun and confine qBittorrent:** do not render global Cloudflare `dns` values. Ensure qBittorrent inherits Gluetun's namespace/DNS behavior, starts only after Gluetun is healthy, and remains addressable to peer services through a network alias on Gluetun or one explicitly declared canonical endpoint.
- **#10 Prove VPN egress and fail-closed behavior:** keep the current public-IP comparison and forced-tunnel failure/recovery proof; a resolver check like the video's final test is at most an additional diagnostic and never substitute evidence.
- **#11 Reconcile qBittorrent acquisition policy:** declare exact `movies` and `series` categories and relative save paths below `/data/torrents`; preserve Automatic Torrent Management; prove idempotence instead of depending on the order of UI clicks.
- **#12/#15 Prepare Radarr/Sonarr:** declare `/data/media/movies` and `/data/media/series` roots and the exact corresponding qBittorrent endpoint/categories; test that every service sees identical `/data` paths.
- **#14/#17 Hardlink-import media:** retain a legal end-to-end item and assert source/destination inode equality, not merely successful import.
- **#21/#22 Stream libraries:** require Jellyfin's media mount to be read-only in rendered topology as well as disabling destructive deletion in policy.
- **#29/#30 Backups:** treat all environment-specific application config volumes as secret-bearing mutable state and verify the manifest includes each one.

## Version and maintenance concerns

- The reviewed repository is a small tutorial artifact: two files, no declared license, no tagged releases, and six commits as of 2026-08-14. The Compose file was added on 2026-01-21; subsequent commits through 2026-02-01 changed the README rather than establishing a release process. [commit history](https://github.com/automation-avenue/arr-new/commits/main/) [Compose history](https://github.com/automation-avenue/arr-new/commits/main/docker-compose.yml)
- `latest` makes the repository's behavior time-dependent even when its YAML is unchanged. Image-specific environment variables, built-in healthchecks, API behavior, and config migrations must be verified against this repository's independently selected pinned images.
- The upstream uses Hotio images but does not justify that vendor boundary. Do not infer that UID/GID variables, secret-file support, healthchecks, or startup behavior are portable across Hotio, LinuxServer, official, and upstream application images.
- The README says Docker Desktop can run the stack, but its Compose file assumes Linux absolute host paths (`/etc/localtime`, `/docker/appdata`, and `/data`). The Home Media Stack's supported Ubuntu/WSL workflow still needs platform-aware host-path validation; the tutorial is not cross-platform evidence.

## Decisions made during plan integration

1. The canonical acquisition endpoint exposed to peer services is `http://qbittorrent:8080`, implemented as a `qbittorrent`
   network alias on Gluetun while qBittorrent shares Gluetun's network namespace.
2. Declared Configuration uses `runtimeUID` and `runtimeGID`. The wizard visibly suggests values derived from the current
   user, suggests `1000` only when it actually matches, and retains the declared timezone field.
3. Compose renders a portable bounded logging policy for every long-running service using the `json-file` driver with
   `max-size: 10m` and `max-file: 3`.
